## Kod końcowy (stan 2026-11-15, 1:1 z pliku)

```csharp
List<string> products = new List<string>();
decimal total = 0;

while (true)
{
    Console.WriteLine("Product name (or 'end'):");
    string name = Console.ReadLine() ?? "";

    if (name == "end")
    {
        break;
    }

    Console.WriteLine("Price:");
    decimal price;
    while (true)
    {
        string priceText = (Console.ReadLine() ?? "").Replace(',', '.');
        if (decimal.TryParse(priceText, System.Globalization.CultureInfo.InvariantCulture, out price))
        {
            break;
        }
        Console.WriteLine("That is not a number. Try again:");
    }

    products.Add($"{name} - {price}");
    total = total + price;
}

Console.WriteLine();

foreach (string product in products)
{
    Console.WriteLine(product);
}
Console.WriteLine($"Items: {products.Count}");
Console.WriteLine($"Total: {total}");
```

## Trzy wyjątki tej sesji — wszystkie z JEDNEJ linii

| Wpis przy cenie | Co się stało |
|---|---|
| `end` | `FormatException` — tekst zamiast liczby |
| `3.00` | `FormatException` — **kropka**, a polski Windows wymaga przecinka → patrz „kultura" niżej |
| `price` | `FormatException` — tekst zamiast liczby (słowo zamiast liczby) |

Wszystkie trzy: `System.FormatException` → `System.Decimal.Parse` → `Program.cs:wiersz 13` (potem 14, po dojściu linii z `priceText`). **Trzy objawy, jedna przyczyna:** `decimal.Parse` nie ma żadnego zabezpieczenia i każdy tekst, który nie jest liczbą, kończy program. To była **moja** wina — `Parse` dałem w bloku 2026-11-14, powinien być `TryParse`.

## Kultura liczb — `decimal.Parse` czyta wg USTAWIEŃ SYSTEMU

- Polski Windows: separatorem dziesiętnym jest **przecinek**, więc `"3.00"` **nie jest** liczbą → `FormatException`.
- `3,00` przechodzi bez problemu.
- Ten sam bug zdarzył się w Shopie (2026-10-26, pole ceny: `149,99` zapisało się jako `14999`).
- Naprawa: `Replace(',', '.')` + `System.Globalization.CultureInfo.InvariantCulture` → działają **obie** formy (`4,50` i `4.50`).

## Nowe pojęcia, które weszły

- **`products.Count`** — **właściwość** (property), nie metoda i nie klasa: składowa `List`, która mówi, ile jest w środku. Wielka litera `C`, **bez nawiasów**, oddaje `int`. Kompilator wie o niej z **typu** zmiennej (`List<string>`), nie z nazwy.
- **`?? ""`** — „jeśli `null`, weź pusty napis”. Wstawia się **raz, przy źródle** (`Console.ReadLine()`), nie przy każdym użyciu zmiennej. Dla liczb wartość zastępcza to `?? 0`.
- **`decimal.TryParse`** — próbuje zamienić tekst na liczbę i oddaje `true`/`false`, zamiast rzucać wyjątkiem. `out price` znaczy „jeśli się udało, wpisz wynik do `price`”, dlatego `decimal price;` może stać bez wartości.
- **Trzy koszyki nazw:** język C# (`new`, `if`, `while`, `break`, `=`, `==`) · .NET (`List`, `Console`, `ReadLine`, `Parse`/`TryParse`, `CultureInfo`) · własne (`products`, `total`, `name`, `price`, `product`). Rozstrzyga **F12** — definicja z .NET otwiera plik spoza projektu.
- **C# a .NET:** C# = reguły zapisu (sam nic nie uruchamia), .NET = uruchamia kod i daje gotowe klasy. `string`/`decimal` to aliasy `System.String`/`System.Decimal`; .NET uruchamia też F#/VB.

## Historia linii `Items` — trzy podejścia

1. `int quantity = products;` + `Console.WriteLine($"Items"{quantity});` — lista zamiast liczby (**CS0029**) i klamry **poza** napisem. Komentarz użytkownika: „coś tam wydukałem ale no slabo”.
2. `Console.WriteLine($"Items{products.Count}");` — mechanizm poprawny, brakowało tylko etykiety: ekran dałby `Items2` (kompilator milczy, bo napis jest poprawny).
3. `Console.WriteLine($"Items: {products.Count}");` — weszło w całym pliku; ekran `Items: 2` ✅.

**Wniosek:** dwukropek i spacja są **wewnątrz** cudzysłowu i to one decydują o wyglądzie ekranu; `{ }` muszą stać przed zamykającym `"`.
